## 4. What is not written down anywhere else

### 4.1 D1: the batching, as the instruction to follow on day one

`docs/mac-port/D1-call-site-survey.md` has the categories, the file list and the PR table. What it
does not say is why the order is the order. It is this:

1. **PR 2 is `W3DProjectedShadow.cpp` alone — 34 state-setting calls, one file.** It goes first not
   because it is the biggest but because it is the safest place to find out whether the pixel
   comparison actually works as an acceptance test. State setting that goes wrong shows up as a
   shadow that is obviously wrong, on a scene you can reproduce. If the comparison cannot catch a
   deliberate error here, stop and fix the test before moving anything else.
2. **PRs 3 and 4 are the rest of the no-new-API swaps** — 18 sites across eight files, then 19
   shader-constant sites across three. Boring by design, and they clear four whole files out of
   the survey.
3. **PR 5 is `shader.cpp` on its own and must not be batched with anything.** It is the only one of
   the five that can change what is drawn, because it is a bug fix wearing a refactor's clothes
   (§4.2). Bisecting it together with a mechanical swap would waste a day.
4. **PRs 6 and 7 consume PR1's API** — resource creation, then render targets and read-back.
5. **PR 8 is streams and draws, 39 sites, and it is last** because it is the only batch that
   touches the draw path itself, and by then the backend's refusal counters should be near zero,
   which makes a regression visible immediately.

Quote the refusal counters `W3DDisplay.cpp` logs at the end of a `-dx11` run — `no buffer`,
`no texture stage`, `no input layout`, `no program`, `no device object`, `engine shader bound`,
`unmirrored texture` — before and after every one of these PRs. That is the progress meter. The
task file used to name an `Enable_Reports`; there has never been one.

**The number that mattered.** The tree said in three places that the engine reached the D3D9 device
from "236 places". That was written on 2026-09-09 by `bfb60e17` and counted every textual mention
of `_Get_D3D_Device()`/`_Get_D3D()` in `GeneralsMD/Code` — 233 in that commit's tree. The very next
renderer commit the same day, `ef8303a9`, removed 111 of them. **The comment was stale within
twenty-four hours of being written and stayed that way for two weeks.** The comparable figure now
is 125.

The plan's own "60 reaches" was wrong in the other direction, and that is the part worth
remembering: two thirds of the device calls do not look like `_Get_D3D_Device()->` at all. They
look like `LPDIRECT3DDEVICE9 m_pDev = DX8Wrapper::_Get_D3D_Device();` followed by twenty
`m_pDev->` calls — one grep hit, twenty calls. In `W3DWater.cpp` the pointer is a *class member*
assigned at `:960` and `:1174`, so it outlives the function that fetched it. **Any future count of
this surface that greps for the accessor will be wrong by a factor of three.** The real figure is
148 device calls through 89 escapes, plus 22 `DX8CALL` sites outside the wrapper.

Also not in the task file: writing PR1 corrected the survey three times. `SetFVF` already has
`Set_Vertex_Format`; `EvictManagedResources` already has `Flush_DX8_Resource_Manager`; and the
render-target save/restore already exists as `Set_Render_Target(surface, depth)` /
`Set_Render_Target(NULL, NULL)`, which keeps and restores the displaced surfaces itself — a second
stack of one would have fought it. So seven of the "75 needing new API" need none.

### 4.2 `shader.cpp` stage 2 — how to confirm it

Recorded in `WINDOWS-DEBT.md` as a suspected live defect in the shipping Windows renderer,
**unverified**. It is not a port artefact.

`shader.cpp:954-961` and `:1003-1012` set texture stage 2 through raw `DX8CALL`, which expands to
`DX8Wrapper::_Get_D3D_Device()->x` and does nothing else. Compare `dx8wrapper.h:1015-1040`, where
the same call through `Set_DX8_Texture_Stage_State` writes `TextureStageStates[stage][state]` and
then calls `Direct3D11_Mirror_Texture_Stage_State`. So those sixteen calls are invisible to the
D3D11 backend *and* to the wrapper's own shadow state — and the wrapper's redundant-state filter
compares against that shadow. The source's own comment says the quiet part: "bypass the wrapper
since it only supports 2 texture stages".

**To confirm it, in this order:**

1. Run `-dx11` on a scene with a multi-texture shader and read the shutdown log's refusal
   counters. `no texture stage` and `unmirrored texture` are what this looks like from the
   backend's side. A non-zero count there with a fixed frame is the first evidence.
2. Then the D3D9-only half, which is the more serious claim: add a temporary assert in
   `Set_DX8_Texture_Stage_State` that stage 2's cached value matches what the device actually
   holds (`GetTextureStageState`). Run a match. If it fires, the shadow is stale and the
   redundant-state filter has been skipping real state changes — on the default renderer, for
   years.
3. Only then fix it, as D1's PR 5, and only with a pixel comparison. **Do not fix it blind** — if
   the filter has been skipping changes, something downstream may have grown to depend on the
   resulting state, and the fix changes pixels.

### 4.3 B2: the 114 clock reads, and the three that look like the bug

The task file records the conclusion — no wall clock is a simulation input — but not the working.
Every clock read in `GameLogic` was classified by preprocessor guard with a script and then read
individually. All 114 are measurement that ends in a `DEBUG_LOG` or an on-screen statistic. Three
look exactly like the determinism bug and are not:

- **`RailroadGuideAIUpdate.cpp:136`** reads the performance counter and feeds it straight into a
  train's direction, with the comment "absolutely, positively random every call!". It is a
  **deliberate desync harness** — `#ifdef RAILROAD_DESYNC_TEST`, and line 49 is
  `///#define RAILROAD_DESYNC_TEST`, commented out. Somebody built it to prove the network code
  *reports* a desync. I ported it as-is and labelled it rather than deleting it. **When E1 finally
  runs two machines, this is the thing to switch on first**: it is a known-good way to make the
  two disagree, so you can check that the desync detector says so. Nobody else knows it is there.
- **`AIPathfind.cpp`'s search cap counts cells, not milliseconds** (`hitCellCap`). A pathfind that
  gave up after N milliseconds would desync any two machines of different speed. Somebody knew
  that. The `QueryPerformanceCounter` reads around it are the `DEBUG_LOG` reporting how long a
  capped search took.
- **`GameLogic.cpp`'s three `timeGetTime` reads** are the map-loading progress bar and the
  multiplayer lobby's load timeout. Both run before the simulation does.

One more, unrelated to the simulation: `WWLib/srandom.cpp:215` seeds a generator from
`GetTickCount`. Nothing in the tree includes `srandom.h`, so it is dead — but it would matter a
great deal if anybody started using it.

The 32-bit wrap in `Clock_Milliseconds` is deliberate and load-bearing: `SysTimeClass::Reset`
writes `WrapAdd = 0 - StartTime`, which is only correct in 32-bit unsigned arithmetic. The macOS
side truncates on purpose. Callers that store the result in a signed `Int` — `GameLogic::testTimeOut`
is one — were already wrong at 24.8 days and are no more wrong now.

### 4.4 PerfTimer: what I would do about it

The finding is in the plan: `_DEBUG`/`_INTERNAL` builds have not compiled since the x64 migration,
because `GameCommon.h` defines `DUMP_PERF_STATS` in those builds, `PerfTimer.h` compiles
`GetPrecisionTimer` under it, `USE_QPF` is never defined, and the `__asm { RDTSC }` branch is
therefore live — on an x64-only project where MSVC has no `__asm`. B2 replaced the block, so those
configurations should build again.

What is not in the plan is what to do next, and it is three things:

1. **Verify the claim before trusting it.** It rests on reading the preprocessor, not on a
   compiler's answer. On a Windows machine, configure `-DCMAKE_BUILD_TYPE=Debug` at `ef810b6f~`
   (the commit before B2, which is what replaced the block): it should fail to compile
   `PerfTimer.h`. At `HEAD` it should not. If the first half does not fail, my reasoning is wrong
   somewhere and the rest of this section is void.
2. **Then add the configuration to CI.** The reason this survived for years is that nobody builds
   Debug. E2 should build it, not to run it, just to compile it. A configuration nobody builds is
   a configuration that does not work.
3. **Expect more behind it.** `PerfTimer.h` was the first error in that file; there was no second
   because the compiler stopped. The same pattern is what hid `zutil.h:113` behind `zconf.h`.
   Anything guarded by `DUMP_PERF_STATS` or `PERF_TIMERS` has had no compiler look at it in years:
   `PerfTimer.cpp`, `SubsystemInterface.cpp`, `PartitionManager.cpp`, `W3DAssetManager.cpp` and
   `GameEngine.cpp` all call into it. Budget for a second and third error, not one.

## 5. Two measurements to preserve

**`FastCriticalSectionClass` under contention is slow, and it is not new.** Acquiring a contended
one took between **11 milliseconds and 11.4 seconds** across runs of B14's harness, because the
spin's backoff — `ThreadClass::Switch_Thread` — sleeps a full millisecond per attempt. That is
exactly what the Win32 version did (`WaitForSingleObject` on an event nothing ever signals, timeout
1), so it is pre-existing and I left it alone: changing how long the engine's hottest lock waits is
a performance change and B14 was a port. But that lock backs `StringClass`, `WideStringClass`,
`FastAllocator` and `mempool` — every string operation and every allocation in WWVegas. Somebody
should look at it deliberately, with a frame-time measurement, as its own piece of work.

**`ThreadClass::running` was a `volatile bool`, and ThreadSanitizer found it.** Written by `Stop()`
on one thread, read by eight `Thread_Function`s on another. `volatile` orders nothing and is not an
atomic. It worked on Windows by an accident of the compiler — MSVC's default `/volatile:ms` gives
volatile accesses acquire/release semantics; clang gives none — and the failure mode is a worker
that never observes the flag and runs until `Stop()`'s timeout, on every shutdown. It is a
`std::atomic<bool>` now. **TSan went red before a single control had been written**, which is the
strongest provenance a finding can have, because nobody arranged it.

And the part worth keeping for its own sake: **my first draft of the new tests used `volatile bool`
for the flags the worker classes share** — the exact defect I had just removed — and TSan reported
it, in the tests, on the run meant to prove the fix. `volatile` is the reflex. It is wrong every
time. There is now a note saying so at the top of those tests in `test_wwlib.cpp`.
