### The ddraw judgement you asked for: neither B5 nor the D-track — exclude them

Measured, not opined:

- `dsurface.h` and `misc.h` are included by exactly four files: `convert.cpp`, `dsurface.cpp`,
  `ddraw.cpp`, `draw.cpp`. All four are in `WWLib/`.
- `DSurface` appears **nowhere** outside `WWLib/` (searched all of `GeneralsMD/Code` bar `Tools/`,
  which is Windows-only anyway).
- Three of the four are in the `wwlib` target; `draw.cpp` is already not. Somebody started this.

DirectDraw is the pre-Direct3D8 2D surface API. The renderer goes `DX8Wrapper` → D3D9 → D3D11 →
(D4) Metal and never touches it. Giving these to the D-track attaches a dead 2D blitter to the Metal
work, which is worse than useless; porting them under B5 means writing a DirectDraw shim for code
nothing calls. They belong in B6's "trim the link surface" bucket, the same treatment
`simpleplayer.cpp` already got. Excluding them removes 4 of the 40 failures for free.

## 4. What I know that is not written down

**The estimates keep not surviving measurement, and it has happened three times today.** "Guard
`BaseType.h`'s one line and `compression` builds" — it was a *fatal* error masking six more. "`win.h`
is the one thing standing between this project and `wwmath`" — `wwmath` is 24 of 36 before my fix
and 24 of 36 after, because every TU reaching `win.h` gets there via `wwstring.h`, which also has
`<tchar.h>`; guarding one of two just moves the error. The mechanism is always the same: a fatal
`#include` error stops the translation unit, so the *next* problem is invisible until the first is
fixed. **Measure after every fix, not before.** Numbers quoted without a re-measure are a snapshot
of what the compiler happened to reach.

**Calibration — the most transferable thing here.** I made the same mistake twice in opposite
directions, and both times the cause was reporting my first reading instead of my checked one.

- In the B5 survey I said `AsciiString.h`'s `#include "windows.h"` was "a delete with nothing behind
  it, worth doing early". There were four `Interlocked*` intrinsics behind it. I had grepped for
  `HWND|HRESULT|DWORD|windows.h`, and `Interlocked*` is none of those. Someone acting on that line
  would have broken the build in a way that looked like their fault. **Under-described.**
- In B13 I nearly wrote up the `(long *)&m_refCount` punning as a serious bug — a 32-bit atomic RMW
  on a 16-bit field, covering its neighbour. I checked instead: the access was correctly aligned
  (`MEM_BOUND_ALIGNMENT` is 4) and the neighbour is written in exactly one place, on a buffer that
  is not shared yet. It is UB that was corrupting nothing. **Nearly over-described.**

A survey's grep pattern is a claim about what it can see, and it should be stated next to the
survey's conclusions. Mine was not.

**The lock ordering, which nothing else records.** `Unicode → Dma → Pool`, one direction only.
`UnicodeString::releaseBuffer` calls `TheDynamicMemoryAllocator->freeBytes` while holding the
Unicode lock; `DynamicMemoryAllocator::allocateBytesDoNotZeroImplementation` calls into the pool
while holding the Dma lock. Nothing in `GameMemory.cpp` takes the Unicode lock, so there is no
cycle. **If anything ever makes the allocator reach back into a `UnicodeString`, that closes the
cycle and `recursive_mutex` will not save you.** This is in `CriticalSection.h`'s comment and the
B11 task file, and nowhere else.

**Why `CriticalSection` must stay recursive.** `UnicodeString::set` takes the lock at
`UnicodeString.cpp:157` and calls `releaseBuffer()` at `:162`, which takes it again at `:130`, on
the ordinary `&stringSrc != this` branch. Built with `std::mutex` it deadlocks on the *first* call,
single-threaded, deterministically. Agent 3a has confirmed B1 does not move those lines.

**The `Interlocked*` family is where sweeps fail.** All four threading primitives found sideways
were in it. `CreateThread` and `CRITICAL_SECTION` announce themselves; `InterlockedIncrement` in a
one-line inline accessor does not, and `_interlockedbittestandset` is the only all-lowercase name in
the family, so a case-sensitive grep misses it entirely. That cost another agent an hour. The sweep
at `docs/mac-port/THREADING-PRIMITIVE-SWEEP.md` has the method.

**The ODR hazard, still live and still a decision.** `class CriticalSectionClass` is defined twice:
`WWLib/critsection.h:50` and `WWLib/mutex.h:92`. It has never fired because `critsection.h` is
included by exactly one file — `critsection.cpp` — and `critsection.cpp` is **not in the `wwlib`
target**, while `mutex.h` is included by 23 files. Add `critsection.cpp` to the build, or include
`critsection.h` anywhere, and you get a redefinition error in the lucky case and a silent ODR
violation in the unlucky one. I verified this rather than deleting anything. **It is B6's call.**

**`persistfactory.h:133` is a pre-existing Win64 defect, not B10 fallout.**
`uint32 objptr = (uint32)obj;` writes a truncated pointer into the save chunk as an object identity
token for `SaveLoadSystemClass::Register_Pointer` to remap on load. Before B10, `uint32` was
`unsigned long` — 4 bytes on Win64 under LLP64 — so the shipping x64 build has been truncating
64-bit pointers all along. It was lossless on macOS only by accident (LP64), and B10 removing that
accident is what made clang reject it. Two objects colliding in their low 32 bits remap to the same
object. I have **not** traced how much of WWSaveLoad the game exercises, so "latent save/load
corruption on x64" is my reading and not a verified claim.

**zsh does not word-split unquoted variables.** Two of my measurement sweeps silently produced
nonsense — reporting `always.h` missing when it was on the include path — because `$INC` was passed
as one argument. I caught it only because the totals disagreed with each other (37 files in a
36-file library). If another agent's sweep produces impossible numbers, check this first.

## 5. Open questions

- **`WWCOMUtil.h:40` `<oaidl.h>` — B5 or exclude?** It is COM (`IDispatch`, `VARIANT`). My instinct
  is exclude, like WOLBrowser, but I did not trace its consumers. **Owner: whoever takes B5 next.**
- **Who owns `persistfactory.h:133`?** It surfaced from agent 14's B10 measurement but is not B10's
  bug. It blocks 6 `wwmath` TUs. **Owner: unassigned — PM to task.**
- **`WWVegas`'s three critical-section implementations** (`critsection.{h,cpp}`, `mutex.cpp`,
  `mutex.h`'s `FastCriticalSectionClass`) plus `_beginthread` in two places. **Owner: B14,
  agent 8d** — check whether it covered all of them or only `mutex.h`.
- **`AsciiString` and `UnicodeString` now refcount two different ways** — one lock-free, one under
  B11's lock. Deliberately not unified: doing so means either a lock in `AsciiString`'s hot path or
  removing one B11 made load-bearing. Worth knowing; probably never worth doing.
- **The `_DEBUG`/`_INTERNAL` configuration is unbuilt by anyone.** It is the one that compiles
  `AsciiString::validate()` and adds `m_debugptr` to both string structs, so it is the configuration
  where B13's layout claim could fail. `WINDOWS-DEBT.md` says to build it first on Windows.
