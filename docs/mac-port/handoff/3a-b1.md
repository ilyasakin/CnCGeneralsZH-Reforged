## 4. What I know that is not written down

Ordered by how expensive it would be to rediscover.

**(a) macOS's wide C library fails on non-ASCII in the C locale.** `vswprintf`, `vswscanf` and
`fwprintf` return −1 with `errno == EILSEQ` for any character outside ASCII while the process is in
the default `"C"` locale. Measured, not inferred. This is written in `WideCharFns.cpp`'s comments
and in B1's task file. What is **not** written anywhere is the shape of the near-miss: my own
survey told the PM to "widen to wchar_t, call vswprintf, narrow back", the PM wrote it into the
task file, and it would have made every non-English localisation throw `ERROR_OUT_OF_MEMORY` on its
first formatted message, Mac only, with nothing in the log naming why — and it would have passed
review, because the code reads correctly. The fix is a thread-local `uselocale()` guard; the
*control* that makes it trustworthy is the test asserting a plain C-locale `swprintf` still fails on
U+0130 afterwards, i.e. that the guard does not leak.

**(b) `ConnectionManager.cpp:706` and `:718` must not be "simplified".** Written in
`B1-wide-format-sites.md`; repeating it because it is the one thing in this handoff that could
cause a security bug if missed. They read
`TheInGameUI->message(UnicodeString(L"%ls"), unitext.str())`, which looks like a roundabout
`message(unitext)`. It is the opposite: `InGameUI::message` treats its first argument as a `printf`
format, and `unitext` is `"[" + player name + "] " + chat text` with **both halves arriving from the
network**. Passing the constant `L"%ls"` as the format is what prevents a remote player's chat line
becoming a format string. Whoever wrote it knew.

**(c) The 1,016 `L'x'` character literals convert silently.** `L'x'` → `char16_t` is an integral
conversion: **no diagnostic**, for every value that fits in 16 bits, and every value in this tree
does. So unlike `L"…"` the compiler will not hand you this list. 919 are in `Keyboard.cpp`'s layout
tables. In the survey §1.3; **not** in the task file's "Do" list, which is where someone following
the steps would look.

**(d) Two of those need a human, not a script.** `Keyboard.cpp:467` is
`_set_keyname_(L'4', L'$', L'�', KEY_4)` — the third argument is literally U+FFFD REPLACEMENT
CHARACTER, three raw bytes `EF BF BD` in the file. Read with line 466 (`L'3'`, `0x00A3` = `£`) it is
the UK layout and the lost character is almost certainly `€`. **It is already broken differently on
each compiler**: `CMakeLists.txt` passes no `/utf-8`, so MSVC reads this UTF-8 file in the system
ANSI codepage and sees a three-character multicharacter literal, while clang sees U+FFFD. Do not let
a script turn it into `u'�'` and call that a port. The other is
`NetworkUtil.cpp:451-463`, the player-name sanitiser, whose `L'\xd800'`–`L'\xdfff'` test is code
whose *meaning* is "this is UTF-16"; every value fits in 16 bits, so it survives, but it should be
read rather than rewritten.

**(e) `IMEManager.cpp` is the one file where the compiler will not help you.**
`ImmGetCompositionStringW` and `ImmGetCandidateListW` take `LPVOID`, so every Win32→`WideChar`
conversion in that file is silent — no type error, no warning. It is also where the undisguised
width arithmetic lives (`result/2` at :1116, `MAX_COMPSTRINGLEN*2` at :1123 and :1189). Read it line
by line. In the survey §5; worth restating because "the compiler finds it" is true of every other
boundary site and false here.

**(f) `ThreadUtils.cpp:33-78` needs a signature change, not a cast.**
`MultiByteToWideCharSingleLine` fills a `WideChar*` and then does `std::wstring ret = dest;`. That
is a hard error at `char16_t` and no boundary cast fixes it — the *return type* is wrong. It is the
only site in the whole survey where B1 changes a signature. Decide it before the sweep, not during.

**(g) Not written down at all, and the reason this section exists:** twice, something I had read
carefully and stated confidently turned out to be wrong the moment it was compiled or checked
(the locale bug in §4a; the claim that WWVegas' wide strings are unreached by `WideChar`, which was
true of the two files I opened and false of WW3D2, which I had not). Agent 95 independently made the

## 5. Open questions

**(a) Does pulling `Lib/BaseType.h` into WW3D2 drag anything unwelcome? — MEASURED, and the answer
is "don't".** Owner was me; now answered, so nobody need repeat it.

- `Lib/BaseType.h` is **not** reachable from WW3D2 today. Nothing in `WW3D2/` includes it.
- It would bring `#define NULL 0`, `#define min(x,y)`, `#define max(x,y)`, `#define TRUE true`,
  `#define FALSE false`, `#define _AMD64_`, `PI`, `TWO_PI`, `ARRAY_SIZE`, and the whole
  `Real`/`Int`/`Bool` typedef family, into a library that has lived without them.
- Measured collisions: **`PI`/`TWO_PI` — none**, neither is defined in WWMath or WW3D2.
  **`min`/`max` — none**, WWMath spells them `WWMath::Min`/`Max` (capitalised and qualified, so the
  lowercase macros cannot match) and there is no `std::min`/`std::max` in either library.
  **`NULL` — live hazard**: four WWLib headers (`INI.H:73`, `SLIST.H:63`, `SLNODE.H:48`,
  `HASHLIST.H:59`) already define `NULL` as `0L`, `0` or `(0L)`, and `BaseType.h` defines it as `0`.
  A redefinition with a different token sequence is ill-formed.
- **Recommendation: do not include `BaseType.h` into WW3D2 at all.** The three headers need exactly
  one thing — the `WideChar` typedef — not three hundred lines of engine preamble. Either give
  `WideCharFns.h` a small self-contained typedef header instead of `BaseType.h`, or put the typedef
  somewhere WW3D2 can reach without the macros. This sidesteps the `NULL` hazard entirely rather
  than fighting it.

**(b) D-track overlap — decided, no action needed.** `render2d.cpp` has 29 `DX8Wrapper::` sites and
`render2dsentence.cpp` has 2, so D1's later PRs do touch the files B1 must retype. The PM measured
it and ruled that B1 goes first; D1 is stalled after PR1 anyway, because PRs 2–8 need a Windows
machine for pixel comparison. Whoever resumes D1 rebases onto the retype. Owner: whoever takes D1.

**(c) The six `test_widechar_width.inc` tests have never run.** They cannot until `gameengine`
compiles. The committed CRC constant `0x25265B36` was derived twice — by hand from
`XferCRC::addCRC`, and by compiling that function standalone over the same 32 bytes — and never
observed from a run of the test. If it is wrong the test is red from the day `gameengine` builds.
Owner: whoever runs `ctest` first.

## 6. B15 — the wide-format sites

Full write-up in `docs/mac-port/B1-wide-format-sites.md` (`c68009df`). Summary, because the headline
is a decision not to build something:

are two unrelated problems that were being counted as one:

- **25 are `%ls` with a `WideChar*` argument.** Of these, 7 are `format(L"%ls", x)` — an assignment

  left alone.

**After those removals, the number of sites needing a wide format to carry a `WideChar*` is zero.**
The hand-written mini-printf this was heading towards is unnecessary. Sized as a morning, and it
does not need the typedef flip.
