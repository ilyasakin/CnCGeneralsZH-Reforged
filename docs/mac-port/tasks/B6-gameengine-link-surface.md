# B6 — Trim the gameengine link surface

- **Milestone:** M1
- **Depends on:** B1 B2 B3 B4 B5
- **Blocks:** C1 C5 E1
- **Status:** not started
- **Size:** `CMakeLists.txt` lines 515–539, plus whatever stubbing the link errors demand

## Why

This is the task that closes M1, and it is the one with the surprise in it.

`gameengine` is 580 files of game logic that, per its own comment in `CMakeLists.txt`, has "no DX8,
no device code". But look at what it links:

```cmake
target_link_libraries(gameengine PUBLIC
  ww3d2 wwlib wwmath wwsaveload wwdebug wwutil compression debuglib wwdownload
  benchmark eabrowserdispatch profile gamespy
  dinput8 wininet imagehlp imm32)
```

`ww3d2` is the renderer and links `d3d9`. `eabrowserdispatch` is MIDL output generated by a
Windows-SDK tool at build time. `wwdownload` links `wsock32` and `winmm`. `dinput8`, `wininet`,
`imagehlp` and `imm32` are Windows import libraries. So `test_gameengine` — the checkpoint that
proves the engine works — currently drags the entire Windows graphics and networking stack behind
it.

Until this is untangled there is no headless Mac build, because the one target worth running
cannot link.

## Scope

`GeneralsMD/Code/CMakeLists.txt`, the `gameengine` and `test_gameengine` blocks, plus new stub
sources under `GeneralsMD/Code/Stubs/` (which already holds `NullAudioManager.h`, so the pattern
exists).

## Do

1. **Work out what is a real dependency and what is a link-time accident.** The comment at line
   521 says `ww3d2` is on the include path "for `d3dx9math.h` alone: BezierSegment carries
   `D3DXMATRIX`, and DumbProjectileBehavior steers a shell with it". `d3dx9math.h` is vendored
   in-repo and header-only. If that is the whole of it, `gameengine` needs the include directory
   and not the library, and the fix is one line. Check before you believe it.
2. **`eabrowserdispatch`** is COM interface glue for an embedded browser that has not worked since
   Internet Explorer was a system component. `WebBrowser` is a pure-virtual factory on
   `GameEngine`. A null implementation in `Stubs/` satisfies it on macOS.
3. **`wwdownload`** is FTP over winsock, used by the patch downloader. The launcher does updates
   now. Stub it on macOS.
4. **`gamespy`** is CMake-based and portable and its build is already configured here with OpenSSL,
   voice and tests off. Try building it for real on macOS before stubbing it — it is the one item
   on this list that may simply work, and a real one is better than 73 guessed prototypes (which
   is what `CMakeLists.txt` says the alternative was).
5. **`dinput8 wininet imagehlp imm32`** move into the Windows branch.
6. **Keep the link list honest on Windows.** Nothing here is an excuse to drop a dependency the
   Windows build needs. If a stub replaces something on macOS, the Windows side keeps the real one.

## Done when

```console
cmake --build build-mac --target test_gameengine
ctest --test-dir build-mac --output-on-failure
```

`test_gameengine` links and runs on macOS. It boots the memory manager, the name keys and the file
system, parses a real INI file, and — the one that matters most —
`simulation_uses_no_runtime_trig` passes, proving the Mac build's simulation is still going through
`DetTrig` and not clang's libm.

Also green on Mac by this point: `test_wwmath`, `test_wwlib`, `test_wwsaveload`, `test_wwutil`,
`test_compression`, `test_debug`, `wwmath_selfcheck`, `compression_selfcheck`.

And Windows: full build, full `ctest`, `replay-check.ps1`.

## Do not

- Do not stub anything `GameLogic` calls. If the simulation reaches a stub, the Mac build is
  playing a different game and M2 is built on sand. Every stub added here gets a comment saying
  which subsystem calls it and why the simulation cannot.
- Do not reach for `GameEngineDevice`. That is C1.
